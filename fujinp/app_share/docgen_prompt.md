# FUJIN-P アプリの文書作成依頼

添付の JSON は，FUJIN-P のアプリ1つ分をアプシャ（app_share）でエクスポートしたパッケージです．この中身だけを根拠として，ユーザマニュアルと技術仕様書を書いてください．

## 材料の読み方

- `files[]` がアプリ本体です．`path` と `content` を読んでください．
- `registry` に起動情報（blueprints），ダッシュボードのカード（launchers），ライブラリと定数の目録があります．
- `tables[]` に所有テーブルの DDL（SHOW CREATE TABLE の結果）があります．
- `issues[]` に既知の不具合があります．
- `documents` に現行のマニュアルと仕様書が入っていれば，白紙から書かず，それを現状のコードに合わせて改訂してください．入っていなければ新規に書いてください．
- `doc_update` に，この依頼の経緯（文書がコードより古い，または未登録）が記録されています．

## 書き方

- 日本語で書き，句読点は全角の「．」「，」を使う．
- 命題から入る．「Xではなく，Yである」という否定からの入り方や，「〜という誤解を避けるために」といった前置きは使わない．
- コードにない機能を書かない．推測が要る箇所は「コードからは確認できない」と明記する．
- Markdown で，見出しは `##` から始める（`#` の題は使わない）．
- 表は必要なところだけ．箇条書きより段落を優先する．

## ユーザマニュアルに書くこと

利用者の立場で，このアプリで何ができ，どう操作するかを書く．対象読者はアプリの利用者（admin 専用のアプリなら admin）．画面の構成，主な操作の流れ，権限によって見えるものの違い，困ったときの確認順．実装用語（Blueprint，エンドポイント，テーブル名）は出さない．

## 技術仕様書に書くこと

次にこのアプリを改修する人（または生成AI）が現状から始められるように書く．

1. 位置づけ（何のためのアプリで，FUJIN-P の中でどこにいるか）
2. 構成（ファイルとその担当，テンプレート）
3. 権限（誰が何をできるか，どこで判定しているか）
4. エンドポイント一覧（メソッド，パス，内容）
5. テーブル（各テーブルの役割と主要な列．DDL は `tables[]` を正とする）
6. データの流れ（主要な操作が，どの画面からどの API を経てどのテーブルに至るか）
7. 設定と定数（config.py に要るもの，外部サービス）
8. 移設時の注意（他アプリへの依存，環境依存の箇所）
9. 既知の持ち越し（`issues[]` と，コードを読んで気づいた点）

## 出力の形式

次の2つのブロックを，この順に，この区切り記号のまま出力してください．区切り記号の行はそれ自体を含めて出力し，前後に説明文を付けないでください．アプシャがこの記号で2つに分けて取り込みます．

```
<<<MANUAL>>>
（ユーザマニュアルの Markdown 本文）
<<<SPEC>>>
（技術仕様書の Markdown 本文）
<<<END>>>
```
